## 2. Технический стек

Один язык на клиенте и сервере, общие типы для событий WebSocket — меньше рассинхронизации контрактов.

| Слой | Технология | Почему |
|---|---|---|
| Монорепо | pnpm workspaces: `apps/web`, `apps/server`, `packages/shared` | Общие типы и схемы валидации |
| Язык | TypeScript (strict) | — |
| Фронтенд | React + Vite | — |
| Рендер карты | **Konva (react-konva)** | Canvas: zoom/pan, drag&drop, хит-тест фишек, работает с тачем (NFR-04, NFR-05) |
| Состояние клиента | Zustand | Простое хранилище, удобно применять серверные события |
| Бэкенд | Node.js + Fastify | REST для загрузки файлов и создания сессий |
| Realtime | Socket.IO | Комнаты, автопереподключение, подтверждения (ack) из коробки (NFR-01, NFR-06) |
| Валидация | Zod (схемы в `packages/shared`) | Одни схемы на клиенте и сервере |
| БД | PostgreSQL + Prisma | — |
| Файлы | S3-совместимое хранилище (MinIO локально) + `sharp` для проверки и уменьшения изображений | — |
| Тесты | Vitest (unit), Playwright (e2e, несколько браузерных контекстов = несколько игроков) | — |
| Инфраструктура | Docker Compose (web, server, postgres, minio), CI на GitHub Actions | — |

Для MVP хватит **одного инстанса сервера**: состояние активных сессий держится в памяти и пишется в БД. Горизонтальное масштабирование (Redis-адаптер Socket.IO) — после MVP.

## 3. Ключевые архитектурные решения

### 3.1. Сервер — единственный источник истины
Клиент отправляет **намерение** (`token.move`), сервер проверяет права (NFR-03), применяет изменение, увеличивает номер версии сессии и рассылает событие всем. Клиент применяет изменения только по событиям сервера. Для отзывчивости собственное перетаскивание отображается сразу (optimistic UI) и откатывается, если сервер отказал.

### 3.2. Протокол событий
Каждое серверное событие имеет `version` (монотонный счётчик в сессии).

- **Клиент → сервер:** `session.join`, `map.set`, `grid.update`, `token.create`, `token.move`, `token.drag` (промежуточное положение, не сохраняется), `token.delete`, `token.setVisibility`.
- **Сервер → клиенты:** `state.snapshot` (полное состояние), `state.patch` (одно изменение + `version`), `token.dragging` (промежуточное положение, без версии), `error`.
- **Подключение / переподключение (NFR-02, NFR-06):** клиент присылает последнюю известную `version`. Сервер всегда отвечает полным `state.snapshot` (состояние маленькое — десятки фишек, — поэтому дельты не нужны).
- **Перетаскивание:** во время drag клиент шлёт `token.drag` не чаще 20 раз/сек, остальные видят плавное движение; при отпускании — один `token.move`, который сохраняется в БД. Это закрывает NFR-01 без нагрузки на БД.

### 3.3. Координаты
Позиция фишки хранится в **пикселях исходного изображения** (центр фишки). Snap-to-grid (FR-15) вычисляется при перемещении по текущим `grid_scale` и `grid_offset`. Так перенастройка сетки не «сносит» уже расставленные фишки.

### 3.4. Идентификация и роли
- При создании сессии создатель получает `masterKey` (случайный секрет) — он хранится в `localStorage` и позволяет вернуть роль после перезахода (вопрос 4).
- Игрок получает `userKey` при первом входе — по нему он восстанавливает «своего» персонажа.
- Роль определяется на сервере при `session.join` и привязывается к сокет-соединению. Каждое событие проходит проверку по матрице прав (раздел 9 аналитики), вынесенной в одну функцию `can(role, action, target)` с unit-тестами на каждую строку матрицы.
- Скрытые мобы (`visible_to_players = false`) **не попадают** в snapshot и patch, отправляемые игрокам. Скрывать их только на клиенте нельзя.

### 3.5. Уточнённая модель данных
Отличия от раздела 8 аналитики:
- `User` → `Participant` (участник конкретной сессии) + поле `key_hash`, `last_seen_at`.
- `Session` + `master_key_hash`, `version`, `last_activity_at`.
- `Map` + `width`, `height` (размер изображения в px), `preview_url`, `grid_snap` (bool).
- `Token` + `name`, `size` (в клетках, по умолчанию 1), `updated_at`.
- Новая таблица `EventLog` (session_id, participant_id, type, payload JSON, created_at) — вопрос 7.

## 4. Этапы разработки

Оценки — для одного fullstack-разработчика, в рабочих днях.

### Этап 0. Каркас проекта — 2–3 дня
- Монорепо, TypeScript, ESLint/Prettier, Vitest.
- БД: локальный PostgreSQL 15 (Docker Compose с postgres и minio — опционально, на будущее); Prisma-схема и первая миграция.
- Файлы в разработке хранятся на диске; S3/MinIO подключается на этапе 6.
- Fastify + Socket.IO «hello world», Vite + React «hello world».
- CI: lint, typecheck, тесты на каждый PR.

**Готово, когда:** `pnpm dev` поднимает сервер и клиент, страница показывает связь с API, БД и WebSocket; CI зелёный.

### Этап 1. Сессии и роли — 3–4 дня (FR-01, FR-02, FR-10, FR-30, UC-1 п.1–2)
- REST `POST /sessions` → `{ sessionId, inviteCode, masterKey }`.
- Страницы: главная (создать / ввести код), вход по ссылке `/s/:inviteCode` с вводом имени.
- `session.join` по Socket.IO, комнаты по сессии, список участников онлайн.
- Модуль прав `can()` + полное покрытие матрицы тестами.
- FR-02 в MVP: Мастер — всегда создатель сессии (роль не освобождается, т.к. передачи роли нет); все входящие по приглашению — Игроки. Клиент не может запросить роль.

**Готово, когда:** двое в разных браузерах в одной сессии, один — Мастер, второй — Игрок; при перезагрузке страницы роли сохраняются; второй Мастер невозможен.

### Этап 2. Карта и сетка — 4–5 дней (FR-11, FR-12.x, FR-13, FR-18)
- Загрузка изображения: проверка типа по содержимому, размера, разрешения (`sharp`), сохранение оригинала и превью в S3.
- Холст Konva: zoom колесом / щипком, pan перетаскиванием, «вписать карту в экран».
- Слой сетки: рисуется только видимая область (иначе на 8000 px будет медленно).
- Панель Мастера: вкл/выкл сетку, размер ячейки (слайдер + точный ввод), смещение X/Y. Режим калибровки: Мастер обводит одну клетку на рисунке — размер и смещение считаются автоматически.
- Параметры сетки сохраняются в `Map` (FR-12.4) и рассылаются всем.
- Смена карты и возврат к предыдущей (FR-18, UC-4).

Реализация (отличия от наброска выше):
- Картинка отправляется как «сырое» тело запроса `POST /api/sessions/:code/maps` (без multipart), ключ Мастера — в заголовке `X-Participant-Key`. Тип файла определяется по содержимому, а не по заголовку.
- На сервере хранятся оригинал и WebP-превью (до 2048 px); телефоны (`pointer: coarse`) грузят превью.
- Лимиты: 15 МБ, 8000 px по стороне, 20 карт на сессию (карту можно удалить).
- Изменение сетки — событие `grid.update` с версионированием: при пропуске обновления клиент запрашивает `state.sync`. Клиент применяет изменение сразу и отправляет не чаще ~10 раз/сек.
- Калибровка: Мастер обводит одну клетку, размер и смещение считаются автоматически.

**Готово, когда:** Мастер загружает карту, подгоняет сетку; игрок видит ту же картинку и сетку; после перезагрузки всё на месте.

### Этап 3. Фишки мобов и синхронизация — 5–7 дней (FR-03, FR-04, FR-14–FR-17, FR-19, UC-3)
- Палитра иконок мобов; размещение кликом в клетку или перетаскиванием из палитры.
- Перемещение с snap-to-grid (переключатель «свободно / по сетке»), удаление.
- Протокол `token.drag` / `token.move` из п. 3.2, optimistic UI с откатом.
- Скрытие/показ моба для игроков (FR-17) с фильтрацией на сервере.
- Боковая панель: список всех фишек с координатами (в клетках), клик — центрировать карту на фишке (FR-19).
- Запись `EventLog`.

Реализация (отличия от наброска выше):
- Значки мобов — встроенный набор из 20 штук (цветной круг + эмодзи), в базе хранятся как `builtin:<id>`; своя загрузка значков — этап 4 (поле уже допускает URL).
- Состояние и обновления считаются отдельно для Мастера и игроков (комнаты `<сессия>:master` / `<сессия>:player`). Игрокам не уходит ничего о скрытом мобе; чтобы их счётчик версии не расходился, они получают пустой `tokens.changed`.
- Привязка к сетке считается на сервере (`placeToken` в общем пакете), клиент использует ту же функцию для мгновенного отклика и откатывается по `state.sync`, если сервер отказал.
- Моб можно поставить сразу скрытым (засада). Размер 1×1…3×3 выбирается при расстановке; переименование и смена размера после расстановки — в бэклоге.
- Фишки принадлежат карте: при смене карты они остаются на прежней и возвращаются вместе с ней.
- Журнал действий (`event_log`) пишется для создания, перемещения, скрытия и удаления; просмотра в интерфейсе пока нет.
- Для этапа 5: ограничение частоты событий (`token.drag` сейчас делает запрос к БД на каждое событие).

**Готово, когда:** Мастер расставляет и двигает мобов, игрок видит перемещение плавно и с задержкой < 300 мс (замер в e2e на локальной сети); скрытый моб отсутствует в сетевом трафике игрока.

### Этап 4. Персонаж игрока — 3 дня (FR-31–FR-34, UC-2)
- Выбор иконки из набора или загрузка своей (обрезка в круг).
- Размещение своей фишки (одна на игрока), перемещение только своей.
- Проверка на сервере: попытка двинуть чужую фишку / моба / сменить сетку → `error`, состояние не меняется (тест на каждое действие из матрицы).

Реализация (отличия от наброска выше):
- Значок хранится у участника (`participants.iconUrl`), поэтому выбор переживает смену карт; у тех, кто не выбирал, значок по умолчанию (стабильный, зависит от id). Смена значка обновляет все фишки игрока.
- Набор — 16 встроенных значков (эмодзи на цветном круге) + загрузка своего: сервер сам обрезает картинку по центру до квадрата 256×256 и перекодирует в WebP (до 2 МБ на входе), клиент показывает кругом. Ручной обрезки на клиенте нет — отложено в бэклог. Старый загруженный файл при замене удаляется.
- Игрок ставит своего персонажа сам и один раз на каждую карту (`character.place`, проверка на сервере); «по разрешению Мастера» (FR-32) в MVP не делали. Фишка принадлежит карте: при смене карты на новой её нет, а при возврате она на прежнем месте.
- Права: игрок двигает и убирает только свою фишку; Мастер чужих фишек не двигает, не скрывает и не удаляет (по матрице). Это проверено серверными тестами по всей матрице (участник × тип фишки × действие) и подделкой событий настоящим ключом игрока в браузере.
- Известный пробел: если игрок ушёл, его фишка остаётся на карте до смены карты — Мастер убрать её не может. Решить вместе с «передачей роли/исключением участника» после MVP.

**Готово, когда:** выполнены пункты 5 и 6 критериев MVP; e2e-тест с поддельными событиями от игрока подтверждает отказ сервера.

### Этап 5. Надёжность и мобильные устройства — 4–5 дней (NFR-02, NFR-04, NFR-05, NFR-06)
- Переподключение: индикатор «нет связи», автоматический повтор, полный snapshot после восстановления; действия во время обрыва блокируются (не копятся).
- Сохранение состояния в БД с задержкой (debounce) + принудительно при выходе последнего участника; восстановление сессии в память при первом входе после рестарта сервера.
- Тач-жесты: pinch-zoom, перетаскивание фишки одним пальцем vs pan двумя; адаптивная вёрстка панелей (на телефоне — нижняя шторка).
- Производительность: на мобильных грузится превью карты; кэширование слоя сетки; профилирование на среднем Android.
- Rate limit событий на соединение; лимит участников (вопрос 1).

Реализация (отличия от наброска выше):
- Состояние **не держится в памяти**: каждое изменение сразу пишется в БД одной транзакцией (сессия, карта, фишки, версия), а позиции при перетаскивании рассылаются, но не пишутся. Поэтому «сохранение с задержкой и восстановление в память» не понадобилось — рестарт сервера ничего не теряет по построению (проверено тестом перезапуска и в браузере).
- Переподключение: клиент после каждого подключения заново входит в сессию и получает полный снимок. Если сервер сам закрыл соединение (деплой, защита от флуда), клиент возвращается через 1–3 с со случайной паузой; при возврате вкладки из фона или появлении сети проверяет связь сразу. Пинг сервера — каждые 10 с, мёртвое соединение замечается за ~20 с.
- Без связи ничего не копится: действия блокируются в интерфейсе и в коде (буфер socket.io иначе повторил бы устаревшие ходы после возврата), недоведённое перетаскивание откатывается. Баннеры: «нет связи» и «вышла новая версия, обновите страницу».
- Ограничения: на события Socket.IO (по типам, токен-бакет; при систематическом превышении соединение закрывается), на сообщения (100 КБ) и на HTTP по адресу (создание сессии 10/мин, загрузки 20/мин, поиск сессии 60/мин; за прокси — `TRUST_PROXY=true`). Для тестов выключаются `RATE_LIMIT=off`.
- Телефон: панели в сворачиваемой нижней шторке, кнопки не меньше 44 px на сенсорных экранах, отступы под вырезы экрана.
- Производительность (эмуляция телефона, процессор медленнее в 4 раза, карта 8000×5000, 100 фишек): прокрутка 27 → 55 кадров/с, щипок 6,8 → 41 кадр/с, самый долгий кадр 500 → 67 мс. Помогли: мемоизация слоя фишек (React перерисовывал все 100 фишек на каждый кадр), замена размытой тени дешёвым смещённым кругом, один слой под карту и сетку. Отключение слоя попаданий на время жеста выигрыша не дало и убрано. Замеры — на программной отрисовке в headless Edge, на настоящих телефонах цифры будут другими.

**Готово, когда:** выключение сети на 10 секунд и рестарт сервера не теряют состояние; плавная работа на телефоне (визуально без рывков при 30+ фишках).**Готово, когда:** выдёргивание сети на 10 секунд и рестарт сервера не теряют состояние; плавная работа на телефоне (визуально без рывков при 30+ фишках).

### Этап 6. Тестирование, деплой, запуск — 3–4 дня
- E2E-сценарии Playwright на UC-1…UC-4 (2–3 браузерных контекста одновременно).
- Нагрузочный прогон: 20 сессий × 10 участников, интенсивное перетаскивание — проверка NFR-01.
- Деплой: один VPS (Docker Compose + Caddy с HTTPS) или PaaS; бэкапы БД; очистка старых сессий и файлов (TTL 30 дней).
- Базовый мониторинг: логи, health-check, метрики числа сессий/соединений.

**Готово, когда:** все 6 критериев MVP (раздел 11 аналитики) проходят e2e-тестами на продовом окружении.

### Итого
**24–31 рабочий день ≈ 5–6 недель** для одного разработчика. Этапы 2 и 3 частично параллелятся, если разработчиков двое (один — холст/UI, второй — протокол/сервер): тогда ≈ 3,5–4 недели.

## 5. Риски

| Риск | Влияние | Как снижаем |
|---|---|---|

## 6. После MVP (бэклог)

1. Туман войны по областям карты (Мастер «открывает» зоны кистью).
2. Передача роли Мастера.
3. Просмотр лога действий Мастером, отмена последнего действия (undo).
4. Инструменты: линейка расстояния в клетках, зоны заклинаний (конус/круг), отметки-«пинги».
5. Состояния фишек: HP, условия (оглушён, отравлен), инициатива и порядок ходов.
6. Аккаунты (OAuth) и библиотека карт/иконок Мастера между сессиями.
7. Горизонтальное масштабирование: Redis-адаптер Socket.IO, хранение активного состояния в Redis.

## 7. Что нужно до старта

1. Подтвердить или скорректировать допущения из раздела 1 (особенно 2, 3 и UC-4).
2. Выбрать хостинг (VPS или PaaS) и домен.
3. Набор базовых иконок мобов и персонажей (свободная лицензия, например game-icons.net — CC BY 3.0).
