# Внутреннее устройство DnD Map

Документ для разработчиков (и для Claude): как устроен код, почему он устроен именно так и что нельзя сломать. Требования — в `analitika-servis-karta-dnd.md`, история решений по этапам — в `plan-razrabotki.md`, эксплуатация — в `docs/deploy.md`.

**Держите документ актуальным:** меняете протокол, модель данных, инварианты или раскладку модулей — обновите соответствующий раздел в том же коммите.

---

## 1. Обзор

Мастер загружает карту, подгоняет сетку и расставляет мобов; игроки заходят по ссылке и двигают своих персонажей; все видят изменения в реальном времени.

```
Браузер (React + Konva)                       Сервер (Node.js, один процесс)                 PostgreSQL
┌───────────────────────┐   HTTP: создание     ┌──────────────────────────────┐   Prisma   ┌──────────────┐
│ HomePage / SessionPage│──сессии, загрузка ──▶│ Fastify: REST + статика      │──────────▶│ sessions      │
│ useSession (состояние)│   картинок           │ Socket.IO: события, комнаты  │           │ participants  │
│ MapCanvas, TokenLayer │◀═══ WebSocket ══════▶│ сервисы: sessions/maps/      │           │ maps, tokens  │
└───────────────────────┘   события, снимки,   │ tokens/characters            │           │ event_log     │
                            патчи с версией    │ файлы на диске (uploads/)    │           └──────────────┘
                                               └──────────────────────────────┘
```

Ключевые принципы:

1. **Сервер — единственный источник истины.** Клиент присылает намерение («подвинь фишку сюда»), сервер проверяет права и данные, применяет, пишет в БД и рассылает результат. Клиент показывает изменение сразу (оптимистично) и откатывается, если сервер отказал.
2. **Состояние не живёт в памяти сервера.** Каждое изменение — одна транзакция в БД (данные + увеличение версии сессии + запись в журнал). Рестарт сервера ничего не теряет. Исключения — только эфемерное: промежуточные позиции при перетаскивании, кэш прав для них, присутствие (кто онлайн), лимиты частоты.
3. **Права проверяются на сервере одной функцией `can()`** из общего пакета. Клиент использует её же, но только чтобы прятать недоступные элементы.
4. **Каждая роль получает свой вариант данных.** Игроки никогда не получают скрытых мобов — ни в снимках, ни в патчах, ни в перетаскиваниях.

## 3. Общий пакет `@dnd-map/shared`

Всё, что обязаны одинаково понимать клиент и сервер. **Любое изменение контракта начинается здесь.**

| Модуль | Содержимое |
|---|---|
| `events.ts` | `ClientToServerEvents`, `ServerToClientEvents` — полный список событий с типами. `PROTOCOL_VERSION` (сейчас 7) — увеличивать при несовместимых изменениях: клиент сравнивает её с `system.hello` и показывает баннер «обновите страницу» |
| `session.ts` | Роли, лимит участников (10), код приглашения (8 символов без 0/O/1/I/L, `normalizeInviteCode`), схемы имени/ключа/входа, `ParticipantView`, `JoinResult`/`JoinError` |
| `map.ts` | Лимиты картинок (15 МБ, 8000 px, 20 карт), сетка (`GridSettings`, `normalizeGrid` — оффсет всегда внутри одной клетки, `applyGridUpdate`), `MapView`, `SessionState` (снимок), общие `ActionResult`/`ActionError`, `UploadError` |
| `token.ts` | Встроенные значки (`MONSTER_ICONS` 20 шт., `PLAYER_ICONS` 16 шт., хранятся как `builtin:<id>`), `FILES_URL_PREFIX`, `defaultCharacterIcon` (стабильный по id), `TokenView`, `TokensPatch`, схемы действий с фишками, **геометрия**: `snapToGrid`, `placeToken`, `clampToMap`, `cellOf` |
| `obstacle.ts` | Препятствия: виды (`wall` стена, `pillar` столб, `barrel` бочка — у каждого свой «закрывает обзор» по умолчанию), `ObstacleView`/`ObstaclesPatch`, схемы запросов, **геометрия**: `cellsRect` (прямоугольник целых клеток между двумя точками, обрезанный по карте), столкновения диска-фишки с прямоугольниками (`discHitsRect`, `sweptDiscHitsRect`, `segmentRectDistance`), правила `canStandAt` и `canMove`, `tokenRadius` (45% клетки на размер), `describeCells` |
| `vision.ts` | Туман войны: `FogState {enabled, radius, polygons}`, `fogUpdateSchema`, границы радиуса (1–30 клеток, по умолчанию 6), `visionRadiusPx`, `visibilityPolygon(источник, радиус, преграды)` — многоугольник видимости (угловой обход: лучи на углы преград ±ε, пересечения с окружностью, внутренние углы пересекающихся прямоугольников), `pointInPolygon`/`inAnyPolygon`, `polygonTouchesRect`, `partyVision` (по многоугольнику на каждого персонажа). Радиус в пикселях = `(клеток + 0,5) · размер клетки` |
| `permissions.ts` | `can(actor, action, token?)` — матрица прав из раздела 9 требований (см. §6) |

Геометрия общая намеренно: сервер решает итоговую позицию, клиент той же функцией показывает её мгновенно — и они совпадают.

**Координаты.** Все позиции — в пикселях *исходного* изображения карты, центр фишки. Поэтому перенастройка сетки не сдвигает фишки. Привязка: фишка нечётного размера встаёт в центр клетки, чётного (2×2) — на пересечение линий. `placeToken` сначала зажимает точку внутрь карты, потом привязывает, потом зажимает ещё раз (иначе брошенная за край фишка привязывалась к клетке за картой).

## 4. Сервер

### 4.1. Запуск и сборка приложения

- `src/index.ts` — точка входа: читает `.env` из текущей папки (если есть), `loadConfig()`, создаёт БД и приложение, слушает порт, по SIGINT/SIGTERM корректно закрывается (`app.close()`, затем `db.close()`).
- `src/config.ts` — все переменные окружения с zod-валидацией и значениями по умолчанию (таблица в §9).
- `src/app.ts` — `buildApp({ config, db })` собирает всё приложение; тесты вызывают его же. Порядок важен:
  1. HTTP-лимиты (`onRequest`-хук — срабатывает до чтения тела, поэтому поток больших загрузок отбрасывается дёшево).
  2. `/api/health`, маршруты сессий.
  3. Статика клиента (если задан `WEB_DIST_DIR`) + SPA-фолбэк: любой GET не на `/api/` и не на `/socket.io` отдаёт `index.html`; неизвестный `/api/...` — JSON 404.
  4. Socket.IO (`maxHttpBufferSize` 100 КБ, ping 10 с / таймаут 10 с) и `registerRealtime`.
  5. Маршруты карт и значков (им нужен `realtime` для рассылки), `/api/metrics`.
  6. Таймер очистки (первый запуск через минуту, потом каждые `CLEANUP_INTERVAL_MINUTES`, без наложения).
  7. Хуки закрытия: `preClose` разрывает сокеты (иначе HTTP-сервер не закроется), `onClose` закрывает Socket.IO и **дожидается всех обработчиков в полёте** (`realtime.drain()`), чтобы они не писали в уже закрытую БД.

### 4.2. Модули

| Модуль | Ответственность |
|---|---|
| `db.ts` | `PrismaClient` + `ping()` + `close()` |
| `db-utils.ts` | `bumpVersion(tx, sessionId, data?)` — увеличивает версию сессии и `lastActivityAt` в той же транзакции; `logEvent(...)` — запись в `event_log`; `gridOf(mapRow)` |
| `sessions/` | `secrets.ts` (ключ участника — 32 случайных байта base64url, в БД только SHA-256; генерация кода), `service.ts` (создание сессии вместе с Мастером, поиск, поиск участника по ключу, добавление игрока, `touch`), `routes.ts` (`POST /api/sessions`, `GET /api/sessions/:code`) |
| `maps/` | `storage.ts` (`FileStorage`: save/remove/open/list по шаблону имени — посторонние файлы никогда не трогаются), `image.ts` (`processImage`: тип по содержимому через sharp, размеры с учётом EXIF-поворота, WebP-превью ≤2048 px; `processIcon`: квадрат 256 WebP), `service.ts` (снимок состояния по роли, добавить/выбрать/удалить карту, обновить сетку), `routes.ts` (загрузка карты, раздача файлов) |
| `obstacles/` | `service.ts` (добавить/удалить/сменить «закрывает обзор»/очистить; каждое — транзакция с версией и записью в журнал; прямоугольник решает сервер), `view.ts` |
| `vision/` | `view.ts` (чистые функции: `seenByPlayers(фишка, туман)`, `viewFor(роль, сцена)` — вид сцены для роли), `service.ts` (`fogOf(sessionId)` — загружает персонажей и закрывающие обзор препятствия, считает многоугольники; при выключенном тумане — один запрос) |
| `tokens/` | `service.ts` (создать моба, поставить персонажа, двигать, удалить, скрыть; найти для перетаскивания), `patch.ts` (`patchFor(change, role)` — что именно роль должна узнать об изменении), `view.ts` (строка БД → `TokenView`) |
| `characters/` | `service.ts` (смена значка участника + всех его фишек, удаление старого загруженного файла), `routes.ts` (`POST /api/sessions/:code/icon`) |
| `realtime.ts` | Все события Socket.IO: вход в сессию, присутствие, действия с картами/сеткой/фишками/персонажами, рассылки по ролям, кэш прав для перетаскиваний, трекинг обработчиков для `drain()` |
| `rate-limit.ts` | Токен-бакеты: per-socket по типам событий + «злоупотребление → разрыв», per-IP для HTTP |
| `maintenance/cleanup.ts` | Удаление истёкших сессий и осиротевших файлов |

Сервисы получают `PrismaClient` и ничего не знают о Socket.IO; `realtime.ts` и `routes.ts` — тонкий слой: валидация (zod) → права (`can`) → сервис → рассылка.

### 4.3. Модель данных (`prisma/schema.prisma`)

```
sessions ─┬─< participants   (role master|player, keyHash, iconUrl, lastSeenAt)
          ├─< maps ─< tokens (type monster|player_character, ownerParticipantId?, x, y, size, visibleToPlayers)
          ├── currentMapId → maps (SetNull)
          └─< event_log      (кто, что, payload JSON)
```

- `sessions.version` — монотонный счётчик изменений (см. §5.3); `masterKeyHash` — хэш ключа создателя; `lastActivityAt` — для очистки.
- `participants`: уникальность `(sessionId, keyHash)`. Мастер — участник с `role = master`, создаётся только вместе с сессией.
- `maps`: `id` совпадает с UUID в именах файлов (`<id>.png`, `<id>.preview.webp`) — по файлу всегда найдётся карта. `width/height` — после EXIF-поворота.
- `tokens`: **уникальный индекс `(mapId, ownerParticipantId)`** — не больше одного персонажа игрока на карту (у мобов owner = NULL, а NULL в Postgres не конфликтуют). Фишки принадлежат карте: при смене карты они остаются на старой.
- `maps.fogEnabled`/`fogRadius` — настройки тумана каждой карты (миграция `fog_of_war`); у новой карты туман выключен.
- `obstacles`: `mapId`, `kind`, прямоугольник `x, y, width, height` в пикселях изображения (привязан к сетке при создании и больше не «ездит» при её перенастройке — как фишки), `blocksMovement`, `blocksSight`. До 500 на карту. Принадлежат карте: при смене карты остаются на своей.
- Удаление каскадное: сессия → участники, карты, фишки, препятствия, журнал.
- Значок участника: `iconUrl` — `builtin:<id>` или `/api/files/<uuid>.icon.webp`; NULL — значит «значок по умолчанию» (`defaultCharacterIcon(id)`).

Миграции: `pnpm --filter @dnd-map/server db:migrate` (интерактивная!). Если Prisma просит подтверждение в неинтерактивной среде — SQL пишется руками в новую папку миграции и применяется `prisma migrate deploy`; совпадение схемы и БД проверяется `prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script` (должно быть «empty migration»).

### 4.4. Файлы

Хранятся на диске в `UPLOADS_DIR`, отдаются `GET /api/files/:name` с `immutable`-кэшем. Имена — случайные UUID, т.е. ссылка известна только участникам сессии (capability URL). `FILE_NAME_PATTERN` защищает от обхода путей: имя, не подходящее под шаблон, не открывается и не удаляется. `FileStorage` — интерфейс, его можно заменить на S3 без изменения остального кода.

Порядок при загрузке: сначала файлы на диск, потом запись в БД; при ошибке БД файлы удаляются. Оставшиеся после падения файлы подбирает очистка (файлы без ссылок старше часа).

### 4.5. HTTP API

| Метод и путь | Кто | Что |
|---|---|---|
| `POST /api/sessions` `{displayName}` | любой | → 201 `{inviteCode, participantKey}`; создатель становится Мастером |
| `GET /api/sessions/:code` | любой | 200 `{inviteCode}` (канонический) или 404 — до подключения по WS |
| `POST /api/sessions/:code/maps` | Мастер | тело — сама картинка (`Content-Type: image/*`), ключ в `X-Participant-Key`. 201 `{mapId}`; ошибки `UploadError` с кодами 400/403/404/409/413/415 |
| `POST /api/sessions/:code/icon` | Игрок | то же для значка (до 2 МБ) → 201 `{icon}` |
| `GET /api/files/:name` | любой со ссылкой | картинка |
| `GET /api/health` | мониторинг | 200 / 503, если БД недоступна |
| `GET /api/metrics` | мониторинг | подключения, сессии онлайн, память, uptime |

Загрузки — «сырым» телом, без multipart: парсер для `image/*` зарегистрирован в отдельной области Fastify со своим `bodyLimit`.

## 5. Протокол реального времени

### 5.1. События

Клиент → сервер (все, кроме `token.drag`, ждут ответ-ack вида `{ ok: true, ... } | { ok: false, error }`):

| Событие | Кто | Что |
|---|---|---|
| `session.join` `{inviteCode, key}` или `{inviteCode, displayName}` | все | Вход/возврат. Ответ: `self`, участники, **полный снимок** `state`, при создании нового игрока — `participantKey` |
| `state.sync` | участник | Полный снимок своей роли (используется после пропуска обновлений) |
| `grid.update` `{mapId, ...частично}` | Мастер | Сетка; остальным — `grid.changed` |
| `map.select` / `map.delete` `{mapId}` | Мастер | Всем — `state.snapshot` |
| `token.create` | Мастер | Только мобы (тип и владелец с клиента игнорируются схемой) |
| `token.move` `{tokenId, x, y}` | по `can` | Итоговая позиция (сервер привязывает к сетке) |
| `token.delete`, `token.setVisibility` | по `can` | |
| `character.place` `{mapId, x, y, participantId?}` | Игрок / Мастер | Игрок ставит своего персонажа; Мастер обязан указать `participantId` (игрока без персонажа на этой карте). Один персонаж на игрока и карту |
| `character.setIcon` `{icon}` | Игрок | Встроенный значок (загрузка своего — HTTP) |
| `obstacle.add` `{mapId, kind, from, to, blocksSight?}` | Мастер | Две точки в первой и последней клетке; сервер строит прямоугольник из целых клеток (столб и бочка — одна клетка в точке `from`) |
| `obstacle.remove`, `obstacle.setSight`, `obstacle.clear` | Мастер | Убрать; «закрывает обзор» да/нет; убрать все на карте |
| `fog.update` `{mapId, enabled?, radius?}` | Мастер | Только для текущей карты. Радиус в клетках (1–30). Всем уходит `state.snapshot` |
| `token.drag` `{tokenId, x, y}` | по `can` | Промежуточная позиция, без ack, не сохраняется |
| `system.ping` | все | `{serverTime}` |

Сервер → клиент: `system.hello {protocolVersion}` (сразу при подключении), `session.participants` (весь список при любом входе/выходе/смене значка), `state.snapshot` (полное состояние после структурных изменений: загрузка/выбор/удаление карты), `grid.changed`, `tokens.changed` (патч), `obstacles.changed` (патч, одинаковый для всех ролей), `token.dragging`.

### 5.2. Вход, комнаты, присутствие

- Сокет без `session.join` не принадлежит сессии — все действия отвечают `not_joined`. Клиент обязан слать `join` **после каждого (пере)подключения**.
- После входа `socket.data.session = {sessionId, inviteCode, participantId, role}`, сокет в двух комнатах: `<sessionId>` (все) и `<sessionId>:<role>` (для рассылок по ролям).
- Роль берётся только из БД. Запросить роль нельзя: Мастер — создатель сессии, все входящие по приглашению — игроки.
- «Онлайн» = есть хотя бы один сокет участника в комнате (`fetchSockets`). Лимит 10 считается по онлайн-участникам; вторая вкладка того же участника места не занимает.

### 5.3. Версии, снимки и патчи

Каждое изменение увеличивает `sessions.version` в той же транзакции. Патчи (`grid.changed`, `tokens.changed`) несут новую версию. Клиент:
- версия ≤ своей — игнорирует (старьё/дубль);
- версия = своя + 1 — применяет;
- больше — пропустил обновление → `state.sync`.

Снимок читается одной транзакцией `REPEATABLE READ`, чтобы версия соответствовала содержимому.

**Пустые патчи для игроков.** Изменение скрытого моба увеличивает версию у всех. Чтобы счётчик игрока не разошёлся (и он не запрашивал `state.sync` постоянно), игрок получает `tokens.changed` с пустыми списками. Логику «что роль должна узнать» реализует `patchFor` (тестируется отдельно): видит сейчас → upsert; видел, но больше не видит (скрыли/удалили) → remove; не видел и не видит → пустой патч.

### 5.4. Перетаскивание

`token.drag` рассылается отправителем ~20 раз/с (`socket.volatile` — при перегрузке сообщения можно терять). Сервер ретранслирует его остальным: видимую фишку — всем, скрытого моба — только мастерам. Права и видимость берутся из **кэша в памяти** (`dragCache` в `realtime.ts`, TTL 2 с) — проверка через БД на каждое сообщение была узким местом под нагрузкой (p95 621 мс → 38 мс). Кэш сбрасывается синхронно при любом изменении фишки (`emitPatches`) и при любом снимке сессии (`broadcastState` — смена карты), поэтому скрытый моб не утечёт к игрокам из устаревшей записи. Получатель показывает чужое перетаскивание, пока не придёт подтверждённая позиция или 2 с тишины.

### 5.5. Препятствия и движение

Препятствия — статичные прямоугольники; фишка — диск (радиус `tokenRadius`). Игрок не может **закончить** ход внутри препятствия и не может **пересечь** его по прямой от прежней позиции до новой (диск «подметает» полосу; закругление углов учтено — по диагонали мимо угла пройти можно). Проверка — на сервере после привязки к сетке (`obstructed` в `tokens/service.ts`) для `token.move`, `character.place` и `token.create`; ответ `blocked`. Мастер освобождён (`ignoreObstacles`: решает `realtime.ts` по роли). Если препятствие построено поверх фишки, она может выйти из него (препятствия, которые перекрывают её в начале хода, на выходе не считаются), но не может остаться внутри. `blocksMovement: false` — препятствие не мешает ходить (на будущее, интерфейс пока не выставляет). Проверка по прямой, а не по пути перетаскивания: обойти стену по дуге за одно перетаскивание нельзя — надо сделать два хода.

Клиент проверяет то же самое той же функцией: красная обводка фишки при перетаскивании «в стену» (`TokenNode`), а при броске — отказ без запроса и возврат фишки с сообщением (`move` в `useSession`). Сервер остаётся арбитром.

### 5.5а. Туман войны

Мягкий: **сервер не отправляет игрокам то, чего их персонажи не видят**, но файл картинки карты остаётся доступным (мастеру об этом сказано в панели).

- Зрение общее: объединение многоугольников видимости всех персонажей на карте. Один радиус на карту. Памяти исследованного нет. Бочка обзор не закрывает (останавливает только движение).
- `SessionState.fog` содержит многоугольники — обоим ролям (мастеру для подсветки, игроку для затемнения). Игрок получает моба, только если он не скрыт флагом и его центр внутри многоугольника; персонажей игроки видят всегда. **Карта и препятствия видны игрокам всегда** — вне обзора они лишь затемнены на клиенте (стены определяют форму обзора, но не секретны). Без персонажей на карте игрок не видит мобов, а вся карта затемнена.
- Что рассылается при изменениях (`emitPatches`): при выключенном тумане — как раньше; при включённом **любое** изменение персонажа, любое изменение препятствий (оно меняет форму обзора) и любая смена настроек → всем (мастеру тоже) свежий `state.snapshot`; изменение моба → мастеру патч, игроку патч по `seen {before, now}` (появился → upsert, ушёл из поля зрения → remove, вне поля → пустой патч, чтобы версия не разошлась).
- `token.dragging` для моба показывается игрокам только пока позиция внутри многоугольников (`fogCache` с TTL 2 с, сбрасывается `forgetSession`).
- Клиент: `FogLayer` (тёмный прямоугольник и многоугольники с `destination-out`), у мастера туман лишь подсвечивает область (прозрачность 0,35), «Смотреть как игроки» фильтрует фишки теми же правилами и затемняет так же, как у игроков (0,7 против 0,3 у мастера).

### 5.6. Защита от злоупотреблений

- Per-socket токен-бакеты по имени события (`SOCKET_RULES`: `token.drag` 30/с, `grid.update` 20/с, `session.join` 0,5/с — защищает ключи от перебора, по умолчанию 15/с). Превышение → ack `rate_limited` (или молча, если ack не ждут). Больше 200 отказов за 10 с → сокет разрывается.
- Сообщение больше 100 КБ → разрыв (Socket.IO).
- HTTP per-IP: создание сессии 10/мин, загрузки 20/мин, поиск сессии 60/мин; 429 с `Retry-After`. За прокси — `TRUST_PROXY=true`.
- Невалидные данные отсекаются zod-схемами из общего пакета; отсутствующий ack не роняет обработчик.

## 7. Клиент

### 7.1. Структура

- `main.tsx`/`App.tsx` — роутинг (react-router): `/` — `HomePage` (создать сессию / войти по коду), `/s/:inviteCode` — `SessionPage`.
- `socket.ts` — один Socket.IO-клиент на вкладку, `autoConnect: false`, тот же origin (в разработке Vite проксирует `/api` и `/socket.io` на :3000).
- `storage.ts` — `localStorage` (все обращения в try/catch): ключ участника на каждую сессию и последнее имя. Без хранилища пользователь просто войдёт заново новым игроком.
- `api.ts` — HTTP-вызовы и человекочитаемые сообщения об ошибках загрузки.

### 7.2. `session/useSession.ts` — всё сетевое состояние

Машина состояний: `loading → (not_found | need_name | joining) → joined | failed`. В `joined` хранятся `self`, `participants`, `world` (последний `SessionState`) и `connected`.

- **Вход.** `findSession` по HTTP → есть ключ в хранилище? → `connect` → на каждый `connect` шлётся `session.join` с ключом. Новый игрок вводит имя, сервер выдаёт ключ, он сохраняется. `unknown_participant` (ключ протух, БД сброшена) → ключ забывается, снова форма имени.
- **`worldRef`** — текущее состояние, доступное обработчикам сокета без ожидания рендера; `applyWorld` обновляет и ref, и state.
- **Изменения моего персонажа Мастером.** Сервер не присылает отправителю его собственные патчи, поэтому всё, что в `tokens.changed` приходит про персонажа текущего игрока, сделал кто-то другой; `useSession` превращает это в `characterNotice` («Мастер переместил / поставил / убрал вашего персонажа»), страница показывает его тостом.
- **Препятствия.** `ObstacleLayer` (мемоизирован, между картой и фишками): стена — тёмный прямоугольник, столб — серый круг, бочка — коричневый круг; не закрывающие обзор — полупрозрачные с пунктиром. Инструменты Мастера (`ObstaclePanel`, `obstacleTools.ts`): стена — протянуть прямоугольник (во время протяжки карта не двигается, показывается превью целых клеток), столб и бочка — клик по клетке, ластик — клик по объекту, без инструмента клик выделяет объект (флажок «закрывает обзор», удалить; Delete). `useSession.obstacleActions`: добавление ждёт ответ сервера (прямоугольник решает он), удаление и смена флага — оптимистично.
- **Применение событий** — по правилам версий из §5.3; разрыв в версиях → `resync()` (`state.sync`).
- **Действия** (`mapActions`, `tokenActions`, `characterActions`): оптимистично меняют `world` (той же `placeToken`/`applyGridUpdate`, что и сервер), отправляют событие, по ack подтверждают (`confirm` — с проверкой версии) или откатываются через `resync`. Сетка отправляется не чаще 10 раз/с (первое изменение сразу, дальше склеиваются), перетаскивания — не чаще 20 раз/с.
- **Офлайн.** Без связи все действия — no-op/`offline`: иначе буфер Socket.IO отправил бы устаревшие ходы после переподключения. Перетаскивание, брошенное без связи, откатывается.
- **Переподключение.** Обычные обрывы — автопереподключение Socket.IO. Если сервер сам закрыл соединение (`io server disconnect`: деплой, защита от флуда), Socket.IO сам не возвращается — клиент переподключается через 1–3 с со случайной задержкой. При возврате вкладки из фона и событии `online` — проверка связи / `resync`.
- **Версия протокола** — `system.hello` сравнивается с `PROTOCOL_VERSION`, при расхождении `outdated = true` → баннер.

### 7.3. Холст: `components/MapCanvas.tsx`

- Konva `Stage`, вид `{x, y, scale}` в React-состоянии. Карта вписывается один раз на карту (`fittedFor`), дальше масштаб остаётся пользовательским. Телефоны (`pointer: coarse`) грузят превью.
- Слои: (1) картинка **и сетка на одном слое** (каждый лишний полноэкранный слой стоит времени на кадр); (2) `TokenLayer`; (3) прямоугольник калибровки.
- Сетка рисуется `sceneFunc` только в видимой области, по индексам линий (без накопления ошибки), и не рисуется, если клетка мельче 6 экранных px. Видимая область читается из живого трансформа сцены, поэтому сетка верна и во время перетаскивания карты.
- **Щипок** — нативные `touch*`-события на контейнере (capture), а не Konva: пока Konva тащит сцену, она не отдаёт обработчикам второй палец. На время щипка `draggable` сцены выключается и возвращается, только когда подняты все пальцы.
- **Клик по пустой карте** — `onPointerClick` (одно событие для мыши и касания). Раньше были `onClick` + `onTap`, и на телефоне одно касание отправляло два запроса.
- Режимы: `placing` (моб `PlacementSpec` или `'character'`) — клик ставит фишку; `calibrating` — протяжка рисует клетку, по ней считаются размер и оффсет сетки. Drag-and-drop значка из палитры — HTML5 DnD с MIME `application/x-dnd-map-token` (`placement.ts`, данные валидируются).
- `focus` (с `nonce`) — центрировать вид на точке (клик по строке списка фишек).

### 7.4. Фишки: `components/TokenLayer.tsx`

- `TokenLayer` и `TokenNode` обёрнуты в `memo`: прокрутка и зум не должны перерисовывать 100 фишек (это давало 7 кадров/с при щипке на медленном телефоне).
- Позицию узла ведёт Konva (перетаскивание) и твин, а не пропсы: `x/y` задаются один раз при монтировании, дальше — плавный твин к цели (`remote ?? token`) при изменении данных. Новый объект фишки (даже с той же позицией) тоже запускает твин — так работает откат.
- Если фишка перестала быть перетаскиваемой посреди жеста (`movable` стал false — пропала связь), Konva молча бросает перетаскивание без `dragend`: эффект сам останавливает его и возвращает фишку к данным.
- Тень — смещённый тёмный круг, не `shadowBlur` (размытие очень дорого на каждый кадр). Свои значки — картинка, обрезанная кругом (`clipFunc`). Скрытые мобы — полупрозрачные с пунктирной обводкой (их видит только Мастер).
- Нажатие на фишку гасит всплытие (`cancelBubble`), иначе одновременно начиналось бы перетаскивание карты.

### 7.5. Страница сессии и панели

`SessionPage.tsx` → `JoinedView`: шапка со статусом связи и баннером версии; карта; рядом **визуально скрытый список фишек** (`ul.sr-only`, «Гоблин 1, клетка 6, 6») — для экранных чтецов, его же используют e2e-тесты; боковая панель. Панели: `MapControls` (карты и сетка, Мастер), `MonsterPalette` + `TokenList` (Мастер; у персонажей есть «снять с карты», но нет «скрыть»), `PlayersToPlace` (Мастер: игроки без персонажа на этой карте с кнопкой «Поставить», режим расстановки `PlayerPlacement`), `CharacterPanel` (Игрок), `ParticipantList`. Клавиши: Esc — выйти из режимов и снять выделение, Delete — удалить выделенную фишку, если разрешено. На телефоне панель — сворачиваемая нижняя шторка; она закрывается при входе в режим расстановки/калибровки. Без связи панели заблокированы (CSS) и действия не выполняются (код).

## 8. Инварианты — что нельзя ломать

1. Права проверяются на сервере через `can()` по данным из БД. Новое действие без проверки на сервере — уязвимость, даже если кнопки на клиенте нет.
2. Каждое изменение — в одной транзакции с `bumpVersion`, а рассылка патча — только после коммита. Иначе клиенты разойдутся по версиям.
3. Игроку не уходит ничего о скрытом мобе: снимки строятся по роли (`getState(sessionId, role)`), патчи — через `patchFor`, перетаскивания — в комнату мастеров. Тесты проверяют сырой трафик игрока; новое событие с данными фишек должно пройти тот же путь.
4. Роль выдаёт только сервер; клиентские поля роли/типа/владельца отбрасываются zod-схемами (они не `passthrough`).
5. Позиции — в пикселях изображения; итоговую позицию определяет сервер через `placeToken`.
6. Клиент без связи ничего не отправляет и ничего не копит.
7. Любой обработчик события — через `acked(...)`/`track(...)`, чтобы ошибка превращалась в `internal`, а закрытие сервера дожидалось его завершения.
8. Ограничения «один персонаж на карту», лимиты карт/фишек/участников проверяются на сервере; «один персонаж» дополнительно гарантирован уникальным индексом (проверка «прочитал-вставил» не спасает от одновременных запросов).
9. Файлы трогаются только по `FILE_NAME_PATTERN`.
10. При включённом тумане игроку не уходит моб вне поля зрения — ни в снимках, ни в патчах, ни в `token.dragging` (проверяется на сыром трафике в `vision/fog.test.ts`). Любое изменение, влияющее на зрение, сопровождается свежим снимком обеим ролям.
11. Игрок не может поставить фишку внутрь препятствия или провести её сквозь него: проверка на сервере, не только красная обводка на клиенте. Препятствия редактирует только Мастер (`obstacle.edit`).

## 11. Сборка и окружение

- `pnpm dev` — сервер (tsx watch, :3000) и Vite (:5173, слушает **127.0.0.1** явно: на этой Windows-машине `localhost` резолвился только в `[::1]`, а он блокировался).
- `pnpm build` — tsup бандлит сервер (общий пакет внутрь, зависимости внешние) и Vite собирает клиент.
- pnpm 12: разрешения на install-скрипты — `allowBuilds` в `pnpm-workspace.yaml` (не `onlyBuiltDependencies`). Новая зависимость со сборкой (prisma, esbuild, sharp...) требует записи там.
- `apps/server` postinstall запускает `prisma generate`. Если генерация падает с `EPERM ... query_engine...dll.node` — клиент Prisma занят запущенным процессом Node (остановить все процессы `pnpm dev`, в т.ч. дочерние).
- Продакшн: `Dockerfile` (миграции при старте контейнера), `deploy/docker-compose.yml`, подробности — `docs/deploy.md`.

## 12. Известные ограничения и бэклог

- Один экземпляр сервера: присутствие, кэш перетаскиваний и лимиты — в памяти процесса. Для нескольких экземпляров нужен Redis-адаптер Socket.IO и общий кэш/лимиты.
- Файлы — на локальном диске (интерфейс `FileStorage` готов к замене на S3).
- Производительность препятствий (эмуляция телефона, процессор медленнее в 4 раза, карта 8000×5000, 100 фишек): 300 препятствий — прокрутка 40 кадров/с (без них 53), щипок 38 (без них 53). Konva рисует все фигуры слоя, а не только видимые; если понадобится больше — отсекать невидимые или кэшировать слой на время жеста.
- Препятствия: проверка пути по прямой; нет слияния соседних прямоугольников и защиты от дублей (до 500 на карту); нет тонких стен между клетками, дверей; `blocksMovement` всегда true.
- Нет: передачи роли Мастера, тумана войны по областям, просмотра журнала в интерфейсе, переименования/изменения размера фишки после расстановки, ручной обрезки значка, «размещения по разрешению Мастера» (FR-32).
- Бандл клиента ~770 КБ (240 КБ gzip) — стоит разделить (Konva отдельно).
- Производительность измерялась в эмуляции телефона в headless Edge, не на реальных устройствах.
